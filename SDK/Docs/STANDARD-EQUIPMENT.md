# Ordinary apparel and standalone melee - experimental API1.2

Framework author: SweetBriana. Module authors choose weapon, ammunition and armour balance; the framework supplies the supported combat integration and player policy. This internal author kit is separate from native product qualification. Candidate01 remains frozen.

Use schema2 JSON or the public-only `StandardEquipmentConsumer` example, with the same identity only once. The profiles request conversion of existing resolved definitions; they do not create definitions. Require API1.2 and the exact capabilities `integration.standard-apparel.v1` and/or `integration.standard-melee.v1`. The sample C# entry checks assembly contract metadata before entering its new-profile helper, so frozen API1.0/1.1 hosts report structured rejection without binding unsupported profile types.

`ce.standard.apparel.v1` requires complete fixed apparel data: `item.mass` in kg, `item.bulk` and `apparel.wornBulk` in CE-bulk, `armour.sharp` in mm-RHA, `armour.blunt` in MPa, and `armour.heat` as a fraction from0 through1. Carried and worn bulk are independent. The ordinary profile accepts exact audited apparel/component roles and preserves layers, body coverage, graphics, costs and identity. Stuffable armour, custom verbs, behaviour extensions, shields and resource components need separate audited support.

`ce.standard.melee.v1` requires mass/bulk plus every ordinary tool's `damage` in damage, `cooldown` in seconds, `penetrationSharp` in mm-RHA and `penetrationBlunt` in MPa. Tool indexes are zero based and preserve original order. Ordinary tools become CE tools, with no ammunition or fire-mode components. Custom components, special tool damage, body-part attacks, attachments and custom containers are refused. The framework supplies CE attack/parry mechanics; the author supplies all tool values.

Standalone melee must resolve to category `Item` and equipment type `Primary`. Each admitted capacity uses its matching ordinary damage definition (`Blunt`, `Cut`, `Stab`, `Poke`, `Scratch` or `Bite`) with the checked worker, armour and injury roles. Conditional target content (`MayRequire` or `MayRequireAnyOf`), conditional participating maneuvers/capacities/damage, and structural list class overrides need a separate adapter. At native startup the framework checks the admitted tool count, untranslated tool identities and ordered capacities before publishing results. Translated display labels remain supported. A cooperating initializer changing the admitted structure causes a clear readiness refusal. Module authors still choose power, cooldown and penetration values.

The manager distinguishes original data, active values and proposals, and records module/author provenance. Vanilla sharp/blunt fractions cannot become physical CE armour baselines. Their original physical value is unavailable. Native unmanaged base definition values are observed once after startup; this does not promise dynamic tracking of later arbitrary C# changes. Per-instance quality/stuff calculation remains CE's responsibility. When a module is off, CE's autopatchers may choose different unmanaged active values. Pending unmanaged fallbacks are not predicted. Player toggles and priority changes are saved for restart and leave active combat values unchanged.

Disabling a conversion provider preserves any independently valid pending winner on an original field such as mass. Only fields without a pending winner receive the unmanaged restart annotation. Malformed C# contributions invalidate their own declaration; healthy declarations continue through the same startup host.

An overriding module must declare its provider dependency. Disabling the provider blocks that dependent integration. Missing required data, unsupported profiles, shape mismatches and incompatible effective plans withhold the applicable managed plan rather than partly converting content. Apparel/melee targets do not join the managed ranged magazine/resource ledger.

The example values are author balance examples, not framework defaults. The kit validates declarations against original resolved XML snapshots and contains no game binaries or playable core mod. Native lifecycle, UI and selected-stack receipts must be assessed separately before use in a colony.
